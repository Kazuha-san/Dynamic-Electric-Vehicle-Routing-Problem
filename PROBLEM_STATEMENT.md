# Problem Statement

**Project Title:** Self-Play Reinforcement Learning for Dynamic Electric Vehicle Routing in Simulated Cities

**Category:** Reinforcement Learning / Combinatorial Optimization
**Type:** Minor Project — Software Only

---

## 1. Background and Motivation

The Vehicle Routing Problem (VRP) is a classical NP-hard combinatorial optimization
problem: determine delivery routes for a fleet serving a set of customers at minimum
cost. The **Electric Vehicle Routing Problem (EVRP)** adds the constraints that make
electrified logistics hard — limited battery range, energy consumed per unit distance,
and the need to divert to charging stations mid-route.

Classical approaches use exact solvers (MIP, branch-and-price) or hand-crafted
metaheuristics. Exact methods do not scale; heuristics do not generalize. Recent work
has shown that combinatorial problems can be reframed as sequential decision-making
"games", letting self-play reinforcement learning methods developed for Go and Chess
learn routing policies directly.

However, the existing RL-for-EVRP literature almost universally solves a **single,
static instance with a fleet size fixed in advance, on synthetic Euclidean coordinates**.
Real delivery operations are none of those things: orders arrive continuously, the
number of vehicles to dispatch is itself a decision with real cost, and vehicles drive
on streets rather than straight lines.

## 2. Problem Definition

Given:
- A city represented as a **real road network**, with a single fixed depot (company HQ)
  and a sparse, fixed set of charging stations.
- A **stream of customer orders arriving over time**, each with a location and a demand.
- A fleet of identical electric vehicles, each with limited freight capacity, limited
  battery capacity, and a fixed energy consumption rate per unit distance.

Determine, for each planning window:
1. The **minimum number of vehicles** required to serve the outstanding orders.
2. An assignment of orders to those vehicles.
3. A route per vehicle such that:
   - every assigned customer is visited exactly once;
   - the vehicle's battery **never** depletes below zero at any point, with charging
     stops inserted as needed;
   - total travel cost along the road network is minimized.

### MDP formulation (per vehicle)

- **State:** current position, remaining battery, remaining load, set of unvisited
  customers. This is the smallest representation satisfying the Markov property — the
  *order* of past visits does not affect what is reachable next, so it is excluded.
- **Action:** the next point of interest to travel to (customer, charging station, or
  depot), selected from a mask of legal moves.
- **Reward:** negative incremental road-network travel cost per step, plus a terminal
  bonus on completing all customers and returning to the depot.
- **Termination:** all assigned customers served and the vehicle has returned to depot.

### Hard safety constraint

The vehicle must never be able to strand itself. This is enforced structurally, by
**reachability-lookahead action masking**: an action is legal only if the vehicle can
reach the target *and* still reach some charging station or the depot after arriving.
Stranding is therefore not a penalized mistake the agent learns to avoid — it is an
unconstructible state.

## 3. Objectives

1. Build real road-network city environments (via OSMnx) with fixed depot and charging
   infrastructure, across three structurally distinct topologies (grid, organic,
   dense-irregular).
2. Implement the per-vehicle EVRP as a Gym-style MDP with hard feasibility masking.
3. Implement a deterministic fleet-sizing module producing a justifiable minimum
   vehicle count, plus customer-to-vehicle partitioning.
4. Implement a Gumbel AlphaZero-style neural-guided MCTS agent trained by self-play,
   with no hand-crafted routing heuristics.
5. Integrate the above into an epoch-based dynamic dispatch pipeline handling orders
   that arrive over time.
6. Benchmark against nearest-neighbour, greedy insertion, and OR-Tools across cities
   and instance sizes, including sizes not seen during training.

## 4. Proposed Methodology

1. **City layer:** extract routable road graphs from OpenStreetMap; place depot and a
   sparse charging network; precompute shortest-path cost matrices over points of
   interest so that search-time cost queries are O(1).
2. **Fleet layer:** compute capacity- and range-driven lower bounds on vehicle count;
   partition orders into per-vehicle feasible subsets, incrementing the fleet only when
   partitioning proves infeasible.
3. **Routing layer:** an attention-based policy/value network supplies priors and value
   estimates; Gumbel AlphaZero MCTS turns those priors into search-improved decisions
   under a small simulation budget.
4. **Self-play:** episodes generated by search produce improved policy targets and
   realized costs; the network trains toward them; the improved network drives the next
   generation of search. No opponent — the agent improves against its own prior self.
5. **Dispatch layer:** fixed-interval epochs batch arriving orders; vehicles already en
   route complete their committed plans.
6. **Evaluation:** methods × cities × sizes × seeds, with every run recorded.

## 5. Scope and Constraints

- Software only; no hardware or proprietary fleet data.
- Single depot per city (multi-depot noted as an extension).
- Linear energy consumption and full recharging in v1 (nonlinear charging curves and
  partial recharge noted as extensions).
- Vehicles are independent once partitioned; charging stations are modelled with
  unlimited concurrent capacity in v1.
- Instance sizes tractable on a single machine.

## 6. Expected Outcomes

- A trained agent producing feasible, low-cost routes with a 100% feasibility rate **by
  construction**, verified empirically.
- Quantitative comparison against classical baselines, including optimality gap versus
  OR-Tools.
- Evidence on whether a policy trained on one street topology transfers to structurally
  different ones — a question the existing literature, which trains on synthetic
  Euclidean instances, does not address.
- A reusable, layered simulation platform extensible to other VRP variants.

## 7. Evaluation Metrics

| Metric | Definition |
|---|---|
| Total cost | Road-network travel cost summed over all vehicle routes |
| Gap vs OR-Tools | Signed relative difference against the OR-Tools reference solution |
| Feasibility rate | Fraction of episodes completing without stranding (expect 100%) |
| Fleet size used | Against the computed lower bound — the over-dispatch check |
| Solve time | Wall-clock seconds per planning call |
